PRD-179459 · sub-task PRD-179410 · atendimento-zendesk

Plano da API de Avisos e Mensagens

A rota principal recebe um atendimento (ticket ID) e devolve os avisos que valem para ele agora. O cadastro e a listagem existem para alimentá-la.

1 · Rota principal

Dado um ticket, quais avisos valem agora

GET /zendeskapps/warnings-and-messages/tickets/:ticketId/avisos

Devolve a lista do cliente e a do atendente, avaliando as regras na hora (RN17), na ordem Crítico → Atenção → Informativo e, dentro de cada uma, as mais recentes primeiro (RN22).

2 · Regras

Forma fixa: OU de E, com "não é"

Não há if/else aninhado livre. As regras se somam com OU, os critérios de cada regra se juntam com E, e os valores de um critério valem como OU. Essa forma expressa qualquer combinação.

16 critérios: 14 de cliente (plano, CNPJ, planilha de CNPJ, processo, planilha de processo, status, contrato, ramo, CNAE, natureza, certificadora, regime, UF, cidade) e 2 de atendente (grupo, guardião). Cada critério é um item no código com a sua função de teste. Um motor único avalia as regras, usado pela consulta e pelo alcance.

4 · Persistência

Regras em JSONB, na própria mensagem

avisos_mensagens
  conteudo, criticidade, para_quem
  inicio_em, fim_em      -- UTC
  status                 -- ATIVA | INATIVA
  regras      jsonb
  criterios   text[]     -- p/ filtros da lista
  planos      text[]
  versao      int        -- 409 se mudou

avisos_mensagens_historico  -- só INSERT
  mensagem_id, acao, alteracoes jsonb,
  autor, criado_em
{ "schemaVersion": 1,
  "rules": [
    { "conds": [
      { "criterio": "plano", "op": "is",
        "valores": ["PREMIUM"] },
      { "criterio": "uf", "op": "is",
        "valores": ["SP"] } ] } ] }
  • Por quê: é o formato da especificação e o que o front já monta, o mesmo JSON vai e volta, e o histórico vira um diff simples.
  • Descartado: tabelas por regra/condição/valor (a consulta nunca filtra por valor no banco) e árvore genérica tipo JSON Logic (a tela não monta árvore).
  • Mensagem e histórico na mesma transação. Sem exclusão. Status Agendada e Vencida calculados na leitura.

6 · Alcance e planilha

Como funcionam na tela de cadastro

Alcance

  • A cada mudança nas regras, o front chama POST /alcance (debounce de ~300 ms).
  • A tela mostra "alcança 31 clientes" por regra, o total sem repetir e, para Atendente, os nomes dos guardiões.
  • Total 0: quadro "Ninguém recebe esta mensagem" e o Salvar barra (RN14).
  • O servidor conta sobre um retrato da base de clientes (atualizado por rotina), com o mesmo motor da consulta. Nada é gravado.

Planilha

  • O XLS/XLSX vai para POST /planilhas, é lido e descartado. Não fica em bucket.
  • O servidor valida o dígito verificador, tira os repetidos e confere se existem.
  • O front mostra "arquivo · 145 CNPJs · 5 recusados", a janela com o motivo de cada recusado e "Baixar lista".
  • No Salvar, só o nome do arquivo e os aceitos entram na regra.
