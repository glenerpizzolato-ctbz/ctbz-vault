# Build e imagem

- Monorepo Nx: cada function fica em `functions/<nome>` e vira o Cloud Run `function-<nome>` (Terraform em `terraform/dev|prd/*_cr.tf`).
- O `Dockerfile` da raiz é compartilhado por `email-holerites`, `email-sender` e `html-to-pdf` (roda `npm run build-all`). Só `ia-desvio-conduta` e `pendencias-oportunidades` têm Dockerfile próprio. Mudar a imagem base na raiz afeta todas as functions que o usam.
- Dev e prd são o mesmo serviço (mesmo Terraform em `terraform/dev|prd`), mas em 2026-10-28 rodavam imagens de épocas diferentes: dev usa a imagem única `experts-functions:<versão>` (ex: `0.1.14`, dez/2025), e prd ainda serve a antiga `function-<nome>-prd:<commit>` (ex: `function-email-holerites-prd:d756c99`, merge da `release/0.15.0`, último deploy em 2025-02-05, revisão 00009-jrv). Ou seja, o prd não recebe deploy desde a troca da pipeline: uma correção só chega lá com um deploy de prd, que precisa ser conferido (`gcloud run revisions list --service <svc> --project contabilizei-experts-prd`).
- O `origin` do clone está em HTTPS; se o push falhar por credencial do glab, usar `git@gitlab.com:ctbz/experts/backend/experts-functions.git`.
- Ver [[cve-2026-111497-node2shell]].

## Deploy de prd falha com 409 (2026-10-28)

- O `deploy-prd` (pipeline 3000677132, merge do experts-functions!5) falhou no `terraform apply` com `Error 409: already exists` para `function-email-holerites`, `function-email-sender`, `function-html-to-pdf`, os tópicos `functions.email-holerites`/`functions.p2p.email-sender` e os triggers do Eventarc. Esses recursos foram criados pela pipeline antiga, antes do state em `gs://ctbz-terraform-state/experts-functions/prd` (backend criado em 2025-12-04); o state só conhece o `function-experts-clientes-emails` e o bucket dele, que foram atualizados normalmente. O dev não tem o problema.
- Correção: blocos `import` em `terraform/prd/imports.tf` (branch `fix/terraform-import-prd`). Depois do import o apply passa a gerenciar esses serviços com a config do Terraform.
- Armadilha: em prd, o `MANDRILL_KEY` está como env var em texto puro, e o Terraform troca por secret `projects/contabilizei-sm-prod/secrets/contabilizei-experts-prd_MANDRILL_KEY`. A SA de runtime (`754947058455-compute@developer.gserviceaccount.com`) tem o accessor pelo vault-roleset desde 2025-11-05 (ver [[vault-roleset/secrets-e-permissoes|secrets-e-permissoes]]); falta só garantir que o secret tem versão com valor. MR do import: experts-functions!6 (draft). O Glener não tem permissão para ler o state nem o `contabilizei-sm-prod`, então o plan local não roda; conferir o plan no job `deploy-prd`.
- Armadilha: os blocos `import {}` (Terraform >= 1.5) **não funcionam** na pipeline: a imagem `contabilizeidevops/gcloud-sdk:latest` tem Terraform antigo, e o `deploy-prd` do merge do experts-functions!6 (pipeline 3000855496) falhou com `Unsupported block type` em `imports.tf`, sem aplicar nada. Com o `imports.tf` em `terraform/prd`, todo deploy de prd quebra (inclusive o `function-experts-clientes-emails`). O caminho é o `terraform import` via CLI, rodado por quem tem acesso ao bucket de state, e remover o `imports.tf`. O `deploy-prd` é manual (botão play).
- Variáveis que a pipeline injeta em prd (para rodar local): `eventrc_sa=contabilizei-experts-prd@appspot.gserviceaccount.com`, `sm_project_id=1046698394190`, `CONTAINER_IMAGE=us-central1-docker.pkg.dev/contabilizei-tools-production/docker/experts-functions`, `CONTAINER_VERSION=<versão do package.json>`.
- O que muda em prd quando o Terraform assumir os serviços (comparado em 2026-10-28): `MANDRILL_KEY` passa de texto puro para secret; `command` vira `npm run start:<function>` (a imagem única não tem CMD); e o `URL_HTML_TO_PDF` do `function-email-holerites` troca de `https://html-to-pdf-gky3vljvwq-uc.a.run.app` (o serviço avulso `html-to-pdf`, de 2024, outro repo) para `https://function-html-to-pdf-754947058455.us-central1.run.app` (a function do monorepo). Ingress (`all`), SA de runtime (compute padrão), memória e Eventarc continuam iguais. Em dev o holerites nem tem `URL_HTML_TO_PDF`, então dev só prova que o serviço sobe, não que gera o PDF.
- Onde a pipeline é configurada: as variáveis do deploy (`CUSTOM_JOB_DEPLOY_IMAGE`, `CUSTOM_JOB_DEPLOY_BEFORE_SCRIPT`, `CUSTOM_JOB_DEPLOY_SCRIPT`, `TF_VAR_*`) vêm do repositório `ctbz/devops/recursos/pipeline`, em `custom/ctbz/experts/backend/experts-functions.yml` (escopo `*`) e `experts-functions.prd.yml`/`.dev.yml` (escopo do ambiente); o `gitops.sh` de lá sincroniza esses arquivos como variáveis de CI do projeto (por isso mudar a variável direto no projeto é sobrescrito). O deploy roda `$TERRAFORM_RESOURCES_SCRIPT` (`cd terraform/$CI_ENVIRONMENT_NAME && terraform init && plan && apply`, com `-lock=false`) dentro do `$GCLOUD_CONTAINER` (`contabilizeidevops/gcloud-sdk:latest`); o `TERRAFORM_VERSION` padrão do componente é `1.4`. Para importar sem acesso ao bucket, dá para sobrescrever o `CUSTOM_JOB_DEPLOY_SCRIPT` no `.prd.yml` com `terraform state show X || terraform import X <id>` antes do plan: feito em [pipeline!3238](https://gitlab.com/ctbz/devops/recursos/pipeline/-/merge_requests/3238) (draft, 2026-10-28), override temporário a remover depois do primeiro deploy-prd com sucesso. Evitar `$1`/variáveis de shell próprias no valor, porque ele vira variável de CI expandida pelo GitLab. O `templates/deploy/template.yml` roda `eval $CUSTOM_JOB_DEPLOY_SCRIPT` sem aspas e sem `pipefail`: as quebras de linha viram espaços (bloco `|` não funciona, só `>` com `&&`). Para lógica com função/loop, o caminho limpo é um `.sh` versionado no próprio repositório da aplicação e chamado pelo `CUSTOM_JOB_DEPLOY_SCRIPT`, já que o conteúdo do arquivo não passa pela expansão do GitLab.

## Deploy de prd com sucesso e regressão do html-to-pdf (2026-10-28)

- O `deploy-prd` do job 17554990919 (com o import via `CUSTOM_JOB_DEPLOY_SCRIPT`) importou os tópicos, os 3 Cloud Run e os triggers do Eventarc e aplicou `0 to add, 4 to change`. Os 4 serviços (`function-email-holerites` 00010-db4, `function-email-sender` 00005-56d, `function-html-to-pdf` 00002-mk6, `function-experts-clientes-emails` 00005-284) ficaram Ready, 100% do tráfego na `experts-functions:0.1.17` (`node:22.23.4-alpine`).
- **Regressão:** o `function-html-to-pdf` passou a responder 500 em todas as chamadas reais (`Failed to launch the browser process! spawn /app/node_modules/puppeteer/.local-chromium/linux-818858/chrome-linux/chrome ENOENT`). A imagem antiga (`function-html-to-pdf-prd:2ebb5e6`, revisão 00001-k2t, que respondia 200) vinha de um Dockerfile próprio (`oven/bun:1.1.27-alpine` + `apk add chromium`, `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium` e `PUPPETEER_LAUNCH_ARGS` com `--no-sandbox` etc.), removido no commit `d20fedf`. O `Dockerfile` da raiz não instala Chromium, e o Chromium baixado pelo puppeteer é glibc, não roda no Alpine. Em dev isso não apareceu porque o serviço só recebia 403 (sem chamadas autenticadas).
- Como o `URL_HTML_TO_PDF` do `function-email-holerites` agora aponta para a `function-html-to-pdf`, a geração de PDF dos holerites também depende dessa correção.
- Rollback rápido: `gcloud run services update-traffic function-html-to-pdf --to-revisions function-html-to-pdf-00001-k2t=100 --project contabilizei-experts-prd --region us-central1` (gera drift no Terraform até o próximo deploy).
- Rollback: o `gcloud run services update-traffic` falhou para o Glener com `PERMISSION_DENIED: artifactregistry.repositories.downloadArtifacts` em `contabilizei-tools-production` (mudar o tráfego revalida a imagem da revisão). Quem tem acesso ao registry (devops) precisa rodar.
- Correção: [experts-functions!8](https://gitlab.com/ctbz/experts/backend/experts-functions/-/merge_requests/8) (branch `fix/html-to-pdf-chromium`), `apk add chromium` + `PUPPETEER_SKIP_CHROMIUM_DOWNLOAD=true` + `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium` no `Dockerfile` da raiz. Validado numa imagem mínima (`node:22.23.4-alpine`, `html-pdf-node@1.0.7`, `puppeteer@5.5.0`): gera o PDF; Chromium 155 e `brotli-libs-1.2.1-r0`. O `html-pdf-node` já lança com `--no-sandbox`.
- Build local: o `docker build` da raiz falha com `E401` no `npm install` quando o token do `.npmrc` (registry npm privado) expira; para testar só o runtime, usar uma imagem mínima com os pacotes públicos.
- Normalizado em 2026-10-28 com a `experts-functions:0.1.18` (revisões `function-html-to-pdf-00003-9r6` e `function-email-holerites-00011-j2k`): o html-to-pdf passou a responder 200 (~1,4 s; 7 s no cold start) a partir de 21:40:18, sem erros nas revisões novas. Os holerites que falharam na janela (51 respostas 500 entre 21:12 e 21:40) foram reentregues pelo Pub/Sub e o backlog zerou às 21:45.
- Holerites: a subscription `eventarc-us-central1-email-holerites-sub-224` tem retry com backoff de 10–600 s, retenção de 24 h e nenhuma DLQ, então uma falha temporária do holerites ou do html-to-pdf não perde mensagem, desde que seja resolvida em 24 h. Para acompanhar: métricas `pubsub.googleapis.com/subscription/num_undelivered_messages` e `oldest_unacked_message_age` pela API do Monitoring.
